# Production deployment and workload budgets

These are initial limits for the public Space Apps deployment. Keep them in one validated server configuration. Change them after measuring representative real cutouts and running the overload checks below.

## Host and public address

The development server has Ubuntu 24.04 LTS, six CPUs, about 11.7 GiB RAM, and about 130 GiB free on the workspace filesystem at inspection. It runs systemd and Caddy 2.10.2. Existing listeners include ports 80 and 443, and the Caddy configuration already contains other routes. Loopback ports 8765 and 8766 were free. The installed workspace Python/Uvicorn and Node runtimes work. The host reached IRSA's public mission page over HTTPS.

Use a dedicated HTTPS hostname on the existing Caddy instance. The server owner needs to provide or approve that hostname and confirm its DNS records, external ingress on ports 80/443, and the way existing Caddy configuration changes are rolled out. The hostname and public reachability remain to be verified from outside this host. Test both address families if publishing both A and AAAA records. [Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https)

The root-owned Caddyfile includes other services and currently has an on-disk `admin off` setting. The installed unit's normal reload command uses the Caddy admin API. Confirm the active configuration and host owner's procedure before cutover. With the admin API disabled, coordinate a controlled restart of the shared proxy or use an existing approved routing mechanism. Validate the complete Caddy configuration and back up the existing files first. Avoid replacing global options, changing other vhosts, or opening a new public TCP port for Uvicorn. [Caddy management commands](https://caddyserver.com/docs/command-line)

## Build and package from GitHub

1. Commit the app, dependency lockfiles, tests, deployment templates, example-generation source and small redistributable demo fixtures to [mt-evvi/nsac](https://github.com/mt-evvi/nsac). Track each derived demo asset's IRSA release, source product IDs and processing revision. Larger artifacts can be released separately with checksums and a reproducible generation command. Keep the checked-in example bundle under 100 MiB total, and keep full FITS files, runtime caches, data dumps, credentials and host-specific configuration outside the repository.
2. Use GitHub-hosted CI with read-only repository permissions for PRs. Install pinned Node/Python dependencies, check types, run deterministic tests and browser smoke tests, build the frontend, and produce a release bundle named with the reviewed git SHA. Include the server package, Vite `dist`, versioned sample manifests/images, dependency hashes, and a manifest/version stamp. The server owner manually stages a reviewed release over the existing SSH path. A future automation can use a protected deployment environment and its own credential. Keep the public repository's PR runner separate from this host. [GitHub runner security](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/add-runners) · [GitHub deployment environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)
3. Deploy from an immutable release directory such as `/opt/nsac/releases/<git-sha>` with a slot symlink under `/opt/nsac/slots/8765` or `/opt/nsac/slots/8766`. Create a production virtual environment inside the release using its pinned lockfile. Do this as the deploy user, then run the app as a dedicated unprivileged service account with no GitHub credentials and no read access to the Codex user's home. The release directory contains only production artifacts. Keep token files, host settings and future API credentials outside the release and out of dotenv files in Git.
4. One Uvicorn process serves the built frontend, manifest JSON, derived images and API under the same origin. Mount only the production asset directories. Serve the app shell for declared browser routes such as `/explore`, leaving missing API/asset paths as real errors. Start with one process so the job admission and archive limits count all expensive work on one backend. Run heavy processing in cancellable child processes or a supervised bounded worker. Use environment caps of one thread per BLAS/native operation. Use a systemd unit with `Restart=on-failure`, `NoNewPrivileges=yes`, `ProtectSystem=strict`, a private temporary directory, and managed writable `StateDirectory`/`CacheDirectory` for each slot. Set `CPUQuota=200%`, `MemoryHigh=1536M`, `MemoryMax=2500M`, and `TasksMax=64` initially. Both slots are temporary during rollout. Only the selected slot accepts public work. [systemd resource limits](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html)

Example unit start command after staging the implementation:

```text
WorkingDirectory=/opt/nsac/slots/%i
ExecStart=/opt/nsac/slots/%i/.venv/bin/python -m uvicorn server.app:app --host 127.0.0.1 --port %i --workers 1 --limit-concurrency 64 --timeout-keep-alive 5 --timeout-graceful-shutdown 15 --proxy-headers --forwarded-allow-ips 127.0.0.1
```

Example Caddy site block for a configured domain:

```caddyfile
spherex.example.org {
    encode zstd gzip
    request_body /api/* {
        max_size 16KB
    }
    reverse_proxy 127.0.0.1:8765 {
        transport http {
            dial_timeout 3s
            response_header_timeout 15s
        }
    }
}
```

Keep Caddy's normal forwarding behavior for direct public traffic and trust only its loopback connection in Uvicorn. Configure the known proxy range explicitly if the server owner uses a separate upstream edge. API requests acknowledge queued jobs quickly rather than holding the connection until IRSA responds. Use HTTPS, same-origin API calls, no public endpoint accepting upstream URLs, and a 16 KB body limit in both proxy and app. [Caddy reverse proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy) · [Caddy request limits](https://caddyserver.com/docs/caddyfile/directives/request_body) · [Uvicorn settings](https://uvicorn.dev/settings/)

## Shared request admission and byte accounting

- Use versioned request handling under `/api/v1`. Expensive work responds `202` with a bounded job ID. `GET /api/v1/jobs/{jobId}` includes the stage, polling delay, explicit limit/coverage/error reason, and any usable partial result. Cache hits return the result immediately. Include source IDs and processing version. Public job IDs expire 10 minutes after completion, with active results retained at least through that window.
- Admit at most 2 active foreground data jobs, of which at most 1 may be an extended analysis (auto-detection across frames, spectra, bulk comparison). Give direct frame requests priority. Keep at most 8 public jobs waiting and a queue timeout of 45 seconds. Enforce at most one active expensive operation per browser session and at most 6 distinct new uncached jobs per minute per client IP, burst 3. Put a short-TTL ceiling on client-rate state. Coalesce concurrent identical work after validation, including across sessions. Shared completed assets and preset playback bypass job admission. Poll at 1 second minimum, backing off to 3 seconds. Cancel obsolete client fetches and drop queued work with no requester. A started shared job can finish within its cap.
- Use max 2 outbound IRSA requests in flight across all users and jobs. Use at most 1 parallel request for optional catalog data. Budget attempted requests and count actual streamed decoded bytes, including retries and truncated responses. Cap the download while reading, with or without `Content-Length`. Use at most 1 retry for transient transport/5xx per upstream request, with jitter, and respect `Retry-After` only when it fits the deadline. Use 3 s connect and 10 s per-response read inactivity limits plus the job wall-clock ceiling. Set an initial upstream transfer ceiling of 8 GiB per rolling 24 hours per live deployment for IRSA and 128 MiB for all catalog overlays. Track remaining budget before scheduling. Pause fresh archive jobs if the circuit opens (3 transient failures in 1 minute, retry eligible after 60 s with one probe). Continue usable cached work.
- Only send documented requests to expected archive/catalog HTTPS endpoints. Validate each returned FITS origin, path and redirects. Require a cutout request with normalized position and bounded size. Do not fall back to full original images from public user requests. Stop on incomplete FITS, a wrong/unsafe-looking product, excess decompressed image dimensions, or total bytes. Inspect FITS headers before accessing image layers. Protect temporary downloads with app-owned paths, per-job deadlines, and a global 1 GiB staging quota per slot.
- Return `422` for invalid geometry/parameters, `413` for oversized request bodies, `429` with `Retry-After` for rate or daily budget exhaustion, and `503` with `Retry-After` for saturation or open circuit. Use stable result reasons such as `LIMIT_REACHED`, `ARCHIVE_TIMEOUT`, `UPSTREAM_UNAVAILABLE`, `INCOMPATIBLE_WAVELENGTH`, `LOW_OVERLAP`, and `NO_COVERAGE`. Report no coverage only for a complete successful search. Preserve usable frames and incomplete metadata with `partial: true`, the exceeded limit, and available date bounds. The viewer keeps its last good frame and lets the user retry the failed item or narrow the field/date range. Never rerun rejected expensive work in the background.

## Per-feature limits

Use native SPHEREx pixel scale for the scientific grid. A larger browser zoom may interpolate on screen without increasing the source pixels or requesting a wider cutout. A public query defaults to 3′ square, accepts 1′–8′, and is at most 128 × 128 scientific pixels per frame. A public FITS cutout may consume at most 12 MiB streamed per response. Ordinary frame work and a quick spectrum share a 64 MiB ceiling per job. Extended spectra have a separate budget. A host probe of a 3′ cutout measured about 4 MB. Limits apply to both measurements and rendering.

| Feature or API | Public starting limits | Response at the limit |
|---|---|---|
| Timeline, interval selector, metadata and shared links. `/api/v1/series` | Archive metadata only on initial lookup. Up to 500 rows per upstream request, 4,000 raw rows, 4 MiB decoded total, 12 upstream attempts and 20 s for one metadata job. Return up to 100 logical timeline entries per page with stable cursor and completeness. When IRSA reports overflow, split request windows and deduplicate the overlaps while budget allows. Changing the time selector groups/indexes the manifest on the client and makes no FITS batch request. Store normalized range, interval and view state in the URL. | Show partial coverage and existing dates. Ask the visitor to narrow dates or load the next indexed page. A missing target interval within partial results is unknown. |
| First frame, playback, blink, FoV. `/api/v1/series/{seriesId}/frames/{frameId}` | Load the earliest available entry in the chosen query and band when the viewer opens. Load selected entries on demand. Preview one nearby frame in either direction. Limit browser transfers for a series to 3 in flight, 8 decoded frame variants and 16 MiB of decoded frame-data memory. At most 6 cutout fetch attempts in one interactive frame job, 64 MiB cumulative and 30 s. Frame image at most 256 KiB crossed on the wire. A FoV change starts one new validated query and aborts superseded UI loads. | Draw the current frame or a date-specific loading/error state. Skip unavailable frames with an explicit indicator. Stop automatic prefetch under busy conditions. |
| Difference heatmap and sum. `/api/v1/series/{seriesId}/comparisons` | One selected pair, 2 aligned science arrays at ≤128 × 128 each, CPU ≤5 s after inputs are ready. No all-pairs comparison. Prepare uncached inputs with ordinary frame calls and shared budgets. Cache result by pair, band, grid and comparison recipe. | Return wait/unavailable with the missing input or masking reason. Never subtract rendered PNGs or compare mismatched wavelengths. |
| Automatic source detection and catalog identity. `/api/v1/series/{seriesId}/detections` | Default to the chosen compatible pair. An explicit extended job may use up to 8 cached epochs, 50 ranked candidates per epoch, and 100 linked candidates total. CPU ≤12 s and no implicit archive fan-out. Reuse the overlay query cache for optional identity matches. | Return ranked partial candidates and tested dates. Keep detections/cross-matches provisional. |
| Manual mark and compare and future path. `/api/v1/series/{seriesId}/tracks` | Up to 8 measured positions per candidate and up to 25 forecast samples. CPU ≤2 s per candidate. No new imagery or archive queries to draw a forecast. Keep each fit separate and fitted only to its dated measurements. | Reject insufficient or ambiguous associations and retain measured separation. Label allowed linear predictions as sky-plane estimates with uncertainty and explicit horizon. |
| Gaia DR3 and WISE catalog overlays. `/api/v1/series/{seriesId}/overlays` | Off until requested. Query one or both of the named catalogs for the displayed field only. Up to 2 query attempts per catalog, 200 rows per catalog, 1 MiB decoded total and 10 s total. Fetch catalog positions/IDs only. If adding Aladin Lite, lazy-load one overview layer at a time and keep the aligned SPHEREx grid authoritative for comparisons. | Show truncation and an optional tighter filter. A timeout leaves the current displayed frames intact. |
| Spectrum. `/api/v1/series/{seriesId}/spectra` | Explicit single selected source and bounded observation period. Return a quick spectrum from up to 8 wavelength samples, using ≤64 MiB of fresh cutouts and ≤30 s. Reuse cached calibration or return a labeled preview with gaps. When the visitor requests an extended spectrum, stage up to 32 probed samples in one job, no more than 128 MiB of fresh cutouts including retries, plus up to 192 MiB of cold calibration fill. Bound the complete extended job to 90 s. Each result is ≤64 KiB JSON with wavelength, units, quality, error and no-data bins. One extended job across the public deployment at a time. Use a position-indexed DR1 cube for an on-demand view of up to 102 nominal channels when a suitably sized server-side query fits the same 12 MiB per response and 64 MiB quick-job caps. Label it as a coadded spectral product with no visit date. A 102-channel visit spectrum needs a separate cache-first batch build. | Report missing samples and the method, coverage and tested dates. Never fill missing channels silently. If precise photometry cannot be validated, label preview values as non-photometric visual samples, or return unavailable. |
| Latest releases and preset regeneration | Allowlist collections in config. Refresh release metadata every 24 h in a host task. Fetch at most 30 MiB of metadata per run. Regenerate the five verified presets outside the public request path with a separate administrative command after review. Initial batch ceiling: one worker, 256 MiB per source, 2 GiB per run, 30 minutes, and ≤2 IRSA requests in flight. Account for shared upstream traffic and schedule outside judging hours. | Keep the last validated preset set until the new set passes checks. Report pending targets or releases rather than replacing working examples with incomplete output. |

Cache validated metadata for 6 hours and allow up to 24 hours stale while refreshing with a visible last-checked time. Cache only confirmed no-coverage results for 10 minutes. Cache catalog overlays for 24 hours. Use content hashes for immutable derived images. Use path/schema versions in cache namespaces for updates to the rendering or astrometry. Apply LRU caps of 2 GiB raw and 4 GiB derived/cache index per slot, 12 GiB aggregate for two slots. Expire raw files after 48 hours. Cache application state and temporary work outside the repo. Reserve at least 20 GiB free filesystem capacity, suspending new data jobs and pruning the non-preset cache before crossing that threshold. Monitor actual preset bundle size, transfer usage and cache hit rate.

## Health checks, cutover, and rollback

1. Stage the new version in the inactive slot. Run `GET /healthz` for liveness and `GET /readyz` to verify the release SHA, manifest schema, static bundle and cache index. Readiness stays healthy when cached examples can run during upstream downtime. Report archive status separately from a recent sampled probe. Do not call the archive on every health check.
2. Run Playwright against the inactive loopback port, allowing the exact loopback origin in the local MCP config for the check. Verify desktop/mobile playback, the five real presets or their documented data limits, direct URL recovery, the comparison heatmap, candidate detection and path gating, and an arbitrary covered coordinate. Verify each optional control calls only the requests allowed for its action. Route through the public hostname after local readiness, then verify the certificate, same-origin APIs, links, and browsing without signing in from an external network.
3. Validate the complete Caddyfile with `caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile` under the host owner's deployment procedure. Preserve its previous route and active release slot. Change only the app vhost route and apply it by the owner-approved method. Pause batch builds around cutover. Avoid two backends processing public archive jobs at once. Store cross-cutover clients' job IDs by release, and return a retryable expiration status after a slot switch.
4. Record structured timing, release ID and stage outcomes with anonymized or short-lived request identifiers. Track archive bytes, cache age/size, active/queued jobs, 429/503 rates, stage duration, worker memory, traffic, and available disk. Alert after sustained queue saturation or upstream failure. Check that 10 concurrent fixture clients preserve cached playback while excess fresh jobs are rejected promptly. Verify a deliberately truncated metadata response stays marked partial, abandoned work stops, and a simulated archive outage leaves all bundled examples reachable. Never log tokens, cookies, or arbitrary request headers.
5. If the public smoke fails, restore the previous route to the last verified slot and apply the same Caddy procedure. Old assets remain served by the old slot while the new slot is stopped and investigated. Keep the last two release bundles and their compatible preset manifests. If HTTPS production ingress cannot be made available in time, use a separately hosted static copy of the real examples as a judging contingency and clearly label live custom lookup unavailable there. The full release check still requires successful public live lookup on the server.
